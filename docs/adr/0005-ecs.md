# 0005 — `bevy_ecs` (standalone) for entities; custom storage for blocks
- Status: Accepted
- Date: 2026-10-22
- Confidence: 70%
- Decided by: Claude (delegated by Adrian: "you decide")

## Context
Terra will have players, mobs, item entities, projectiles, and block entities, plus
mods that add components and behaviour. The server must replicate entity changes to
clients efficiently. Blocks are far too numerous for an ECS: they need dense, bit-packed storage.

## Decision
- **Blocks/chunks/light**: custom data structures in `terra-world` (palette sections, nibble light).
- **Entities**: `bevy_ecs` used standalone (no Bevy engine) inside `terra-sim` on the server,
  introduced in M3. We use its scheduler for parallel systems and its **change detection**
  to drive network replication (send only changed components).
- The client keeps a lightweight entity mirror. It may use `bevy_ecs` too if that proves simpler.
- Pin the `bevy_ecs` version; upgrades are deliberate tasks.

## Consequences
- Mature, fast ECS with system scheduling and change ticks out of the box.
- `bevy_ecs` has major releases every few months, so pinning plus occasional upgrade work is needed.
- Mods (M13) will interact with entities via a host API, not raw ECS access.

## Alternatives considered
- **hecs**: tiny and stable, but no scheduler or change detection, which we'd rebuild ourselves (~60% alt).
- **Hand-rolled structs**: simplest now, scales poorly with many entity types and mods.
- **flecs (via bindings)**: powerful, but C dependency and FFI.
